# V1 产品基线

本文件记录 V1 已由需求方确认的产品约束。原始基线形成于 2026-09-17；2026-10-04 已同步甲方确认的体验架构调整。后续若发生变更，应修改本文件并在提交说明中写明原因。

## 1. 原型权威程度

AIFORCE 提供的九辰保研小程序原型为 V1 高权威需求基线。

- 第一版原则上照原型开发；
- 允许指出明显缺陷和大幅优化空间；
- 未经确认，不擅自改变原型已经明确的页面、流程和字段；
- 优化建议与 V1 实现分轨管理。

## 2. 小程序主体结构

> 2026-10-04 产品体验架构调整已由需求方/甲方确认。AIFORCE 原型仍保留业务字段与已确认业务规则的参考权威，但旧“五入口”信息架构不再作为必须原样保留的约束。实施蓝图见 `docs/design/jiuchen-v1-experience-blueprint.md`。

V1 不是官网简单镜像，也不是固定功能门户，而是围绕用户生命周期、状态变化与当前任务重新组织服务的微信客户端。

### 普通用户 / 学员稳定一级导航

- 首页：回答“现在最值得处理什么”，内容随生命周期与状态变化动态排序；
- 规划：承接原“学堂”的长期规划、当前阶段、老师反馈、辅导记录与版本；
- 机会：承接院校、夏令营、预推免、政策、服务号内容及与当前目标相关的机会；
- 我的：个人事实资产、成长档案、身份、评估历史、履历与输出能力。

以下能力不再永久占用普通用户一级导航：

- “定位 / AI 评估”改为上下文能力：首次建档阶段突出，完成首次评估后退为“当前定位 / 重大变化后的重评建议”；
- “资讯”改为“机会”中的内容来源之一；
- “学堂”产品语义升级为“规划”，底层阶段与辅导规则保持数据驱动。

### 老师一级导航

- 工作台
- 学员
- 辅导
- 我的

### 管理员一级导航

- 工作台
- 用户
- 业务
- 我的

同一角色内一级导航保持稳定，不因某项数据暂时为空而忽隐忽现；动态变化应发生在页面内容优先级，不发生在导航骨架。

## 3. AI 保研评估

V1 直接实现 AI 评估，不采用原型中固定五维权重规则作为核心逻辑。

### 目标

用户提交结构化背景信息后，系统结合院校/项目信息与真实保研案例，由 AI Agent 输出结构化分析结果。

### 原则

- 不使用机械的固定百分比评分作为主要决策逻辑；
- 不允许模型无证据生成精确录取概率；
- 评估结果需要可解释；
- 允许在资料不足时明确表达不确定性；
- AI 模型调用必须位于服务端。

### 评估额度

- 新用户可获得一定免费评估次数，具体数量以最终产品配置为准；
- 免费额度用尽后，可通过微信支付购买评估次数/额度；
- 课程不通过小程序在线购买。

## 4. 数据来源

九辰目前没有自有真实保研案例数据，但存在其他来源的真实保研案例数据。

要求：

- 数据必须保留来源属性；
- 非九辰服务产生的案例，不得宣传为九辰成功案例；
- 涉及个人信息的案例必须脱敏；
- 本地 XLSX/CSV 可作为整理与导入源；
- 线上数据库是生产系统唯一真实状态源。

## 5. 课程

V1 中课程模块只负责：

- 课程展示；
- 课程介绍；
- 在线咨询/联系顾问。

V1 不实现：

- 课程在线支付；
- 课程订单自动开通；
- 拼团、优惠券等电商能力。

## 6. “我的课堂”

V1 按原型提供的初步模型实现，不扩展成完整 LMS。

### 时间轴与展示规则

#### 大一至大三正常学期

展示：

- 绩点规划
- 英语规划
- 竞赛规划
- 科研规划

#### 大三暑假前的所有假期

仅展示：

- 英语规划
- 竞赛规划

#### 大四阶段

只展示：

- 实习规划

#### 大四寒假

只展示：

- 实习规划

### 绩点规划

- 导入学生每学期课程；
- 根据保研目标和课程难度，为每门课程设置目标分数；
- 辅导老师可点击查看老师介绍；
- 辅导记录由后台管理录入。

### 其他规划表

英语、竞赛、科研等规划表总体沿用原型“大一上”板块所展示的交互与信息逻辑。

### 实习规划例外

实习规划表需要删除：

- 辅导老师；
- 辅导/辅导记录相关内容。

## 7. 管理后台

V1 开发范围包含九辰内部管理后台。

当前最明确的后台职责是：

- 公司员工查找学员；
- 按阶段维护“我的课堂”数据；
- 更新绩点、英语、竞赛、科研、实习等规划；
- 录入辅导记录；
- 维护与课堂相关的必要导师信息。

院校、资讯、课程、案例等是否全部纳入后台 CMS，按实际维护频率逐步扩展，不在 P0 阶段强行做大而全后台。

## 8. 微信平台

九辰已具备微信小程序 AppID / 企业主体，微信公众平台开发侧已经准备，可进入后续开发、真机调试和版本上传流程。

敏感凭据不进入 Git 仓库。

## 9. 已冻结技术基础与尚需业务确认的事项（2026-10-09 更新）

已冻结：独立 ECS Fastify API、MySQL 唯一线上业务真相源、CloudBase Storage 适配、Assessment 当前生产模型/结构化规则、管理员首绑与生命周期合同。UI 施工不得重新选型这些基础能力。

仍需另行审批或验证，但**不阻塞 Phase 1a 安全导航重构**：
- 微信支付商户材料、经批准的免费额度及 SKU/价格、生产 schema、回调/退款一致性与真机支付；仅 AI 评估额度允许购买，课程只展示和咨询。
- `staff` 是否需要独立四槽产品体验；过渡阶段仅保留现有 teacher-like 入口与服务端权限，绝不提高至管理员。
- 正式运营中的资讯自动同步 timer、标签回归，部分成长档案/辅导记录生产 Schema 与 DOCX 真机验收。
- 账号删除和跨角色授权审计、用户协议/隐私指引及完整多设备验收。
- 模型微调/训练不是 V1 前置工程。


## 10. 登录、身份与用户协议

V1 使用统一登录入口，不再在登录页区分“学员登录 / 老师登录”。

### 登录方式

V1 只保留两种官方微信生态登录方式：

- **微信一键登录**：使用 `wx.login`，由服务端调用微信登录凭证校验接口并建立业务会话；
- **手机号快捷登录**：使用微信手机号快速验证组件 `open-type="getPhoneNumber"`，一次性 code 只提交服务端，由服务端调用微信官方手机号接口换取已验证号码。

V1 明确不建设：
- 用户名/账号密码登录；
- 密码找回；
- 手输手机号 + 自建短信验证码登录；
- 假验证码或仅前端判断成功的伪登录。

两种登录方式都只解决 User 身份认证，不能直接授予 Student / Teacher / Admin 业务角色。

### 自动注册与游客

- 用户第一次通过可用认证方式登录时，系统自动创建 `User`；
- 数据库内部生成不可见 UUID，用于协议、会话与数据关联；
- 新用户不自动获得九辰业务身份，默认角色为 `user`，用户界面显示为“游客”；
- 游客可以访问公开内容与允许的基础能力，但不能访问老师、学员或管理员专属数据。

### 九辰内部ID

- 九辰内部ID是业务身份，不等于数据库 UUID；
- 学员、老师、管理员分别使用不同前缀的内部ID；
- **2026-10-08 需求方批准、10-09 生产真机通过：**学员（JCS）、老师（JCT）、管理员（JCA）均可由已登录、尚无业务身份的用户凭九辰提供的**真实存在、可用、未认领**的内部ID一次性认领；首个管理员不依赖旧管理员授权。
- JCA 是高权限一次性激活凭证，必须定向私密交付。未知、已绑定或 `disabled` 的 ID 绝不能提权；认领不是前端让用户自行选择管理员角色，而是服务端对真实 ID 及状态做原子校验。
- 输入兼容常见横杠和全角英数字，服务端区分“编号不存在”“已认领/暂停/撤销”等错误；当前**不迁移为纯数字ID**。
- 认领成功后内部ID锁定，用户不能自行修改；登录界面不允许用户选择角色，服务端权威身份决定游客/学员/老师/管理员对应体验。
- 管理员可管理**其他人的**业务 ID：暂停（保留绑定、使原会话暂不可访问）、恢复暂停（原账号恢复）、撤销授权（解除绑定、原账号退回游客、该 ID 禁用）、恢复已撤销ID（重新可认领，不自动授予旧账号权限）。
- 当前管理员不可在工作台暂停或撤销自己的 ID；上述写操作仍由服务端进行权限和状态检查。
- 此处替代旧文档“管理员必须由已有管理员/电脑后台完成绑定”规则，不得因旧日志恢复初始化死循环。

### 用户协议与会话

- 登录页必须提供用户协议勾选；
- 当前开发阶段允许使用占位协议正文，但系统记录协议类型、版本、同意时间与对应用户；
- 微信身份用于首次认证，API 后续访问使用服务端签发的随机会话令牌；
- 权限判断必须在服务端完成，不依赖前端传入的角色或 userId。

### 退出与注销

- 退出登录只撤销当前会话，不改变业务身份与业务数据；
- 注销账号撤销全部会话、解除当前登录凭据、清理用户自填资料；
- 注销不得由用户自行删除九辰内部 Student / Teacher 业务档案；
- 已绑定内部ID在账号注销后进入禁用状态，由管理员后续处理；
- 业务档案、辅导记录等公司业务数据与用户登录账号生命周期分离。

## 11. 用户资料收集

用户自行填写的学业背景与签约学员业务档案分开管理。

第一阶段资料采集至少包含：

- 本科院校；
- 专业；
- 当前年级；
- 绩点 / 均分；
- 专业排名。

原则：

- 仅在业务明确需要时增加字段；
- AI 定位、“我的资料”等页面复用同一份本人资料，不重复建立多套事实源；
- 签约后的 `Student` 仍是九辰服务学员档案，不与普通用户自填资料强行合并；
- 涉及真实个人信息的生产数据不得进入 Git。

## 12. 手机管理员工作台

管理员在小程序“我的”中拥有独立管理工作台，首批覆盖：

- 创建、绑定、解绑、禁用或删除内部业务ID；
- 查看游客 / 学员 / 老师 / 管理员账号状态；
- 新增或移除老师—学员分配关系；
- 触发九辰教育微信服务号动态同步。

完整课堂编辑、批量数据维护等复杂操作继续保留在电脑端内部后台。

## 13. 动态 / 资讯同步

V1 优先同步九辰教育微信服务号已发布内容，不要求运营人员在小程序重复人工发布。

- 服务号 AppID / AppSecret 仅保存在服务端环境变量；
- 同步通过微信官方发布能力接口实现；
- 小程序数据库保存标题、摘要、封面、原文链接、发布时间与来源标识；
- 若服务号当前账号无对应接口权限，则保留手工录入作为后备路径，不采用非官方抓取作为默认生产方案。


## 14. Production 部署方向

业务方当前期望小程序后端与九辰教育官网共用公司已有阿里云服务器，但必须隔离运行。

已确认原则：
- 官网与小程序可以共用物理主机；
- 不共用项目目录、Node 进程、环境变量、发布脚本、日志和 rollback 生命周期；
- 小程序 API 应作为独立容器或独立系统服务；
- 官网继续保持静态站点运行方式；
- 小程序崩溃或发布失败不应直接导致官网进程退出；
- Production 服务号同步必须使用稳定/固定公网出口 IP。

2026-10-09 实际生产已采用独立 `jiuchen-api.service`、不可变 release 和受控回滚，核心 API 通过 `https://api.jiuchenedu.com` 对外提供服务。该生产路径已有用户提供的发布/健康检查证据，**不是尚待重新选择的架构**。

电脑 Vue 管理后台的正式生产发布/域名/账号审计仍需专项核验；本地开发后台接口存在不代表其已在生产启用。早期部署候选见 Proposed ADR-0008，仅作历史参考。

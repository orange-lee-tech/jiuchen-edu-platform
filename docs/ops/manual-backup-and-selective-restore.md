# 九辰教育自主手动备份与选择性恢复规范

**文档日期：2026-10-29**  
**适用范围：九辰教育微信小程序后端、公司官网及共享入口**  
**性质：运维合同、操作流程与验收边界；不包含密码或密钥。**

> 核心原则：九辰采用由项目方管理员在自己的电脑上主动执行的自主备份流程。腾讯云 CloudBase 是线上业务数据的运行平台，不是本项目唯一的备份保障。本规范不要求购买额外云备份套餐、部署常驻 Mac mini 或依赖 GitHub Actions 执行备份。

## 1. 备份目标与责任边界

### 1.1 为什么采用自主备份

- 备份触发权、加密密码和备份文件由项目方管理员掌握。
- 备份覆盖跨云业务组件，不把某一家云厂商的控制台快照视为完整项目备份。
- 备份操作在管理员自己的 WSL Ubuntu 环境中执行，服务器只提供受控的采集接口。
- 备份文件默认保存在管理员本地 Linux 文件系统中，不能依赖 ECS 本机磁盘保存唯一备份。
- 支持按网站、小程序后端或全部范围制定恢复计划，避免一次故障导致不相关业务被覆盖。
- 恢复前先核验备份、依赖、目标和数据丢失窗口；生产覆盖需要单独授权。

### 1.2 备份责任分工

| 资产 | 主要责任方 | 本流程负责什么 |
|---|---|---|
| ECS 上的 API、Node 运行时、私有案例文件 | 项目方管理员 | 通过受控 SSH 采集、加密保存并验证 |
| 腾讯 CloudBase MySQL | 项目方管理员与数据库维护者 | 通过现役 API 数据库连接路径导出 SQL，保存加密副本并在隔离 MySQL 中恢复验证 |
| 官网文件 | 项目方管理员 | 归档官网当前实际指向的 release 和静态资源 |
| Nginx / Nginx Proxy Manager / TLS 证书 | 项目方管理员 | 作为共享入口单独备份；恢复前审查路由、证书和代理配置差异 |
| 微信小程序代码 | GitHub 仓库 | 由 Git 历史和固定 commit 保存；本地配置与未提交工作仍须另外保护 |
| AI 服务商、微信商户、云平台账户 | 项目负责人 | 通过独立受控渠道管理凭据、权限与账单；不得将密码写入本文件 |

GitHub 代码历史不包含线上数据库真实业务数据、ECS 环境密钥、证书私钥和全部未跟踪运维资产。因此 GitHub 不能替代全资产备份。

### 1.3 备份工具与运行位置

仓库内工具：

- tools/maintenance/start.sh
- tools/maintenance/maintain.py
- tools/maintenance/remote_snapshot.py
- tools/maintenance/test_maintenance.py
- tools/maintenance/README.md

管理员运行环境：Windows 上的 WSL Ubuntu 24.04。工具放在 WSL Linux home 目录，例如 ~/jiuchen-maintenance；备份放在 ~/jiuchen-backups。

**不要把唯一备份放在 Windows 挂载盘（例如 WSL 的 /mnt/c）、ECS、GitHub、CI 日志、聊天记录或公开网盘。** 工具会拒绝把备份根目录直接放在 /mnt/ 下的共享挂载路径。

不要求常驻 Runner。自托管 Runner 可以执行工程测试，但不是备份计划的调度器，也不是备份文件的长期存储位置。

## 2. 七个已定义的备份组件

备份工具以组件化归档生成加密的 .jcb 文件。每个组件可单独选择；即使 scope 选择 all，也不意味着所有组件自动入选。

| 组件 | 默认采集来源 | 典型文件 | 敏感等级与注意事项 |
|---|---|---|---|
| database | 腾讯 CloudBase MySQL 的现役业务数据库 | database.jcb | 最高敏感；含用户档案、课表、评估、订单、额度账本等真实业务数据 |
| user-files | /opt/jiuchen-api/shared/cases | user-files.jcb | 高敏感；私有案例与可能包含个人信息的业务文件 |
| api | /opt/jiuchen-api/current 解析到的真实 release | api.jcb | 高敏感；程序包可能含内置案例、历史误放配置或其他敏感资料 |
| runtime | Node.js 22 运行时目录 | runtime.jcb | 需与实际 systemd ExecStart 使用的运行时路径核对 |
| website | /www/wwwroot/jiuchen-current 实际指向的官网 release | website.jcb | 可能包含历史配置、发布时写入的个人资料 |
| secrets | /etc/jiuchen-api 与已登记的 API systemd unit | secrets.jcb | 最高敏感；环境变量、API 密钥、服务配置 |
| entry | /etc/nginx、Nginx Proxy Manager 的 data、letsencrypt 和自定义 app/index.js | entry.jcb | 最高敏感；代理账号、证书私钥、共享入口配置 |

### 2.1 共享入口的 SQLite 处理

Nginx Proxy Manager 的 SQLite 数据库不能在运行时简单复制活动数据库文件。工具会使用 SQLite 在线 .backup 生成一致性快照，再运行 PRAGMA integrity_check。归档中用快照替换活动数据库文件，避免将不一致的 SQLite 主文件、WAL、SHM 和 journal 混在一起。

恢复 entry 组件会影响共享入口，不是普通的“小程序后端文件恢复”。恢复前必须审查官网与 API 的 Proxy Host、证书、路由、端口和外部 include，且需要独立授权。

### 2.2 runtime 路径必须核对

备份脚本历史配置中定义的 Node 运行时路径为 /opt/jiuchen-api/runtime/node-v22.23.3-linux-x64；2026-10-29 的 systemd 现场输出显示运行命令使用 /opt/jiuchen-api/runtime/node/bin/node。

这两种路径可能通过链接或目录布局关联，也可能存在配置漂移。**不能仅凭 runtime.jcb 已生成就认定它覆盖了当前正在运行的 Node 二进制。** 每次正式备份验收都应把实际 ExecStart、真实路径和 runtime 归档内路径核对一致。

## 3. 备份范围与选择规则

工具提供三种业务 scope：

| scope | 允许组件 | 使用场景 |
|---|---|---|
| website | website | 官网文件故障，且不需要更改共享入口 |
| miniprogram | api、user-files、database、runtime | 小程序后端程序、案例文件、数据库或运行时故障 |
| all | 七个组件均可被选择 | 跨业务或共享入口故障，需要综合评估 |

secrets 和 entry 属于共享或敏感依赖。只有显式选择 all scope 并明确列出相应组件时才纳入计划；选择 all 不会自动把所有组件都选中。

常见选择性恢复计划：

~~~bash
# 网站文件
bash start.sh plan --backup "$HOME/jiuchen-backups/实际备份目录" --scope website --components website

# 小程序 API 程序；不恢复数据库
bash start.sh plan --backup "$HOME/jiuchen-backups/实际备份目录" --scope miniprogram --components api

# 小程序数据库：先计划，再隔离恢复
bash start.sh plan --backup "$HOME/jiuchen-backups/实际备份目录" --scope miniprogram --components database

# 组合恢复计划；共享配置仍必须显式列出
bash start.sh plan --backup "$HOME/jiuchen-backups/实际备份目录" --scope all --components website,api
~~~

恢复计划应明确本次目标 scope、选择的组件、源路径与目标路径、默认保留的现役配置和数据库、共享依赖影响、隔离目标、回退点和可能的数据丢失窗口。

## 4. 管理员日常操作流程

以下命令在管理员 WSL 中执行。实际路径以本机已核验的工具目录为准。

### 4.1 运行只读诊断

~~~bash
cd ~/jiuchen-maintenance
bash start.sh doctor --host root@121.40.168.181
~~~

doctor 只检查已知源路径是否存在、API 服务和已知源站是否能响应等基础状态。它不能证明数据库内容正确、DNS/TLS 正常、用户业务可用或所有外部资源都被覆盖。

如首次 SSH 连接，先核对服务器主机指纹。禁止为了让脚本运行而关闭 SSH 主机校验。

### 4.2 创建加密备份

~~~bash
cd ~/jiuchen-maintenance
bash start.sh backup --host root@121.40.168.181 --output ~/jiuchen-backups --pin
~~~

操作要求：

1. 备份密码在交互提示中输入，不作为命令行参数，也不写入日志。
2. 密码应与加密备份文件分开保管。
3. 工具逐组件生成归档、加密文件和回执。
4. 任一必需组件失败时保留 PARTIAL 状态，不把该代备份当作完整成功版本。
5. 不删除前一代备份，不用失败的数据库文件覆盖上一份成功文件。
6. 管理员只回传脱敏状态、组件名和结果，不回传 SQL、备份文件或密钥。

### 4.3 失败后断点续传

~~~bash
bash start.sh backup --host root@121.40.168.181 --output ~/jiuchen-backups --pin --resume-latest
~~~

续传流程只选择最近的合规 PARTIAL 代；已完成组件必须先通过密文哈希和解密认证，再原样复用，不重新下载或覆盖。只补齐未完成的组件。不同组件的采集时间可能不同，不能因此宣称获得跨组件统一时间点快照。

### 4.4 数据库连接专项检查

历史现场曾遇到 MySQL TLS 错误。工具加入了条件传输逻辑：

- 若 MySQL 服务端支持 TLS，客户端要求 TLS。
- 若服务端不支持 TLS，默认拒绝无 TLS 的远端数据库地址。
- 在项目负责人明确接受现役连接路径的情况下，工具可显式使用 --accept-existing-db-route 复用当前生产路径；这是历史兼容例外，不是端到端加密证明。

只读检查命令：

~~~bash
bash start.sh db-check --host root@121.40.168.181 --accept-existing-db-route
~~~

如果工具输出 DB_TRANSPORT=EXISTING_PRODUCTION_DB_ROUTE_NO_TLS_EXPLICIT，说明 ECS 到数据库这一段沿用的现役路径没有 MySQL TLS 保护。不得把该输出解释成全链路加密，也不得擅自关闭数据库安全设置或更改网络。应另行治理数据库传输安全。

### 4.5 隔离数据库恢复演练

~~~bash
bash start.sh rehearse-db --backup "$HOME/jiuchen-backups/实际备份目录"
~~~

工具使用管理员 WSL 中已有的 MySQL 8.0 镜像，在独立、禁网的临时容器内导入 SQL，检查数据库表并在结束后清理本次临时容器与卷。它不应连接生产写库，不会把 SQL 导入 ECS 生产数据库。

隔离导入成功只能证明 SQL 能在该隔离环境中导入，并能执行有限的表检查。若要验证生产迁移兼容性，还需恢复生产结构副本并执行本次确切候选的迁移，再核对关键业务数据。

### 4.6 选定组件上传到 ECS staging

~~~bash
bash start.sh stage --backup "$HOME/jiuchen-backups/实际备份目录" --scope website --components website --host root@121.40.168.181
~~~

该操作将选定组件解密后上传到 ECS 私有 staging，比较上传前后的 SHA-256。它不切换官网目录、不切换 API current、不执行生产 SQL，也不自动恢复生产环境。上传的明文暂存资料仍然敏感，必须按审批后的恢复或作废流程管理。

## 5. 加密、校验、权限与保留规则

### 5.1 加密格式

现有工具使用 AES-256-GCM 对归档加密，使用 Scrypt 从管理员密码派生 256 位密钥；每个组件独立生成随机 salt 和 nonce；认证标签覆盖加密内容，头部作为附加认证数据。解密或认证失败时删除不完整的明文目标文件。

加密文件无法用普通文本编辑器直接阅读。密码丢失将无法恢复内容，因此密码不能与备份文件放在同一个目录或同一份未加密文档里。

### 5.2 本机权限

- 备份根目录权限：0700。
- 备份文件与临时凭据文件权限：0600。
- 使用 WSL Linux 文件系统，避免把含密钥的明文解压到公共 Windows 桌面。
- 正常退出时工具会清理临时明文；强制杀进程、断电或系统崩溃后，仍需人工排查临时残留。
- 不宣称对 SSD、文件系统或异常退出后的残留实现了安全擦除。

### 5.3 完整性验证

每个组件至少需要：

1. 下载完整；
2. 记录 SHA-256 等校验信息；
3. 解密认证成功；
4. 归档成员安全检查通过；
5. 组件必需文件齐全；
6. 数据库组件另行完成隔离导入和检查。

文件存在或哈希匹配不等于数据库可恢复。加密认证通过不等于业务数据与生产逐行等价。

### 5.4 三代保留原则

目标策略是保留三套相互独立、可恢复的完整备份集合，包含正式发布前需要的固定恢复点。当前三代算法有合成测试，但自动轮换/删除并未完成生产接入。

- 不要按日期直接删除旧备份。
- 不要删除唯一可用的数据库恢复点。
- 增量备份不是当前已交付能力；在完整基线、增量事件、删除标记、结构版本、依赖关系和整链恢复都通过之前，不得用增量文件替代完整备份。
- 程序文件可以按哈希去重；用户历史数据不得为节省空间而做有损特征提取或未经授权删除。
- 若未来采用增量，旧基线被依赖时不能清理；须先合并出新的完整基线并验证恢复。

## 6. 恢复策略：从诊断到生产授权

### 6.1 第一原则：先诊断，再决定是否恢复

先区分 API 进程故障、数据库连接故障、数据库结构缺失、用户文件缺失、官网文件故障、DNS/证书/共享代理故障，以及外部微信、模型服务商或 OCR 服务故障。

API 健康失败不一定需要恢复数据库；官网外网打不开也不一定需要覆盖官网文件。先使用 doctor 和只读检查确定故障域，避免把正常数据覆盖掉。

### 6.2 默认恢复动作

| 故障 | 默认处理 |
|---|---|
| API 程序版本损坏 | 先尝试现有不可变 release 回滚；需要时只计划恢复 api |
| Node 运行时故障 | 核对实际 ExecStart 和 runtime 归档后再恢复 |
| 私有案例或用户文件缺失 | 单独恢复 user-files，先核对覆盖范围 |
| 数据库健康失败 | 先诊断网络、凭据、TLS、服务端状态和结构；优先隔离恢复 |
| 官网文件损坏 | 只恢复 website，不触碰 API 与数据库 |
| NPM/证书/共享入口损坏 | entry 单独评审，逐路由核对后恢复 |
| 环境配置不兼容 | 默认保留现役配置；逐项比较差异，不用旧备份覆盖全部现值 |

### 6.3 网站、小程序和全部恢复的边界

- **website**：官网文件与静态资源恢复，不更改 API、业务数据库和共享代理。
- **miniprogram**：后端 API、运行时、私有案例和数据库可分别计划；不要默认同时恢复所有组件。
- **all**：不是“一键覆盖一切”。网站、小程序、数据库、secrets、entry 仍需逐组件选择并审查依赖。
- **entry**：属于共享入口，可能同时影响官网与 API，必须单独批准。
- **database**：默认只做隔离恢复；生产数据库覆盖需说明恢复点之后的新增订单、评估、资料和额度流水会丢失或需要合并的风险。

### 6.4 生产恢复必须单独授权

进入生产覆盖前必须确认目标组件、目标路径、固定备份代和数据时间点；当前生产状态及现役/回滚版本；新鲜备份的组件完整性和密码可用性；隔离恢复结果；生产与备份之间的数据丢失窗口；网站与共享入口的影响范围；回滚方案和明确授权。

当前工具只提供组件加密下载、计划、隔离演练和受控 staging；不能把它当作已完成的全资产自动生产恢复系统。

## 7. 已知覆盖缺口与不能宣称的事项

以下边界必须长期保留，直到取得新的盘点和恢复证据：

- CloudBase Storage 中的持久对象、临时上传文件和所有外部对象是否全部纳入备份，尚未形成完整覆盖证明。
- 官网附属数据库或额外外部数据源尚需盘点。
- /etc/nginx 外部 include、证书实际引用路径、systemd drop-in、额外 timer、维护脚本依赖等可能超出现有 secrets/entry 组件的已知范围。
- Harbor、Portainer 及其全部持久化卷只作为同机基础设施依赖登记；本流程不等于这些系统已完成整机可恢复备份。
- 备份组件之间没有统一停写点，不宣称数据库、文件、代理配置和代码具有严格的跨组件同一时间点一致性。
- 生产数据库链路曾出现 MySQL TLS 不可用的现场证据。使用显式现役连接路径导出时，应如实记录传输边界。
- 仅有备份文件、doctor PASS、SHA-256 PASS 或数据库导入成功，都不能宣称完整业务恢复成功。

建议在备份合同台账中继续保留：

- fullBusinessCoverage=false，直到 CloudBase Storage、网站附属数据和共享入口依赖都完成覆盖审计；
- productionBackupRestored=false，直到生产恢复策略和受控生产恢复验收完成。

隔离恢复通过是重要证据，但不应把它改写成生产恢复通过。

- ECS 的 /root/jiuchen-backups 约 101 MB；
- ECS 的 /opt/jiuchen-backups 约 24 KB；
- 两处发现的归档主要是 2026 年 6 月的旧网站/Nginx 备份；
- 没有在这些 ECS 目录中找到当前小程序后端和 CloudBase MySQL 的完整恢复证据。

这与“备份保存在管理员 WSL 本地”并不矛盾。它说明**不能把 ECS 上这两个旧目录当成当前完整备份的来源**，也不能通过服务器磁盘上的旧 tar.gz 推断数据库可恢复。

### 8.3 当前维护结论

- 继续由项目方管理员定期执行本地加密备份。
- 生产数据库结构变更前，使用最新可验证备份恢复到隔离 MySQL，并演练该次确切迁移。
- 先核实运行时归档路径、CloudBase Storage、网站附属数据和共享入口依赖，再决定能否将覆盖状态标记为完整。
- 不把腾讯云控制台的自动备份、ECS 上的旧网站归档或 CI 通过当作这套自主备份合同的替代证据。

## 9. 每次备份应保存的验收记录

建议每一代备份至少保留下列元数据，不保存秘密值：

| 字段 | 内容 |
|---|---|
| generation | 备份代标识与创建时间 |
| operator | 执行人或责任角色 |
| host identity | 已核验的目标主机标识 |
| components | 每个组件的选择、状态和采集时间 |
| artifact hash | 每个加密组件的 SHA-256 |
| encryption check | 认证解密是否通过；不记录密码 |
| database export | 导出阶段结果、表数和数据库版本；不记录连接串 |
| isolated restore | 是否导入隔离 MySQL、表数、迁移版本和校验结果 |
| scope coverage | 本代覆盖的业务范围及未覆盖资产 |
| retention status | 保留理由、是否被其他增量依赖 |
| approval | 若涉及生产恢复，记录单独审批编号或时间 |
| unresolved risks | 未闭合风险与下一步动作 |

管理员回传的内容以脱敏状态和结果为主。SQL、真实用户数据、环境变量、证书私钥和密钥不进入 GitHub、聊天或 CI。

# 核心领域模型（初稿）

本文件用于在写业务代码前统一概念。字段级数据库 Schema 会在 P1 进一步设计。

## 1. User

微信小程序用户。

核心关系：

- 一个 User 可拥有评估额度；
- 一个 User 可产生多次 AI Assessment；
- 签约后可关联 Student 学员档案。

## 2. Student

签约学员的业务档案。

可能包含：

- 基础身份信息（最小化保存）；
- 本科院校、专业等保研相关背景；
- 当前培养阶段；
- 保研目标；
- 规划时间轴；
- 关联导师；
- 辅导记录。

User 与 Student 不应强行视为同一实体：普通用户可以使用 AI 评估但不是签约学员。

## 3. AcademicStage

学员时间轴中的阶段，例如：

- 大一上；
- 大一寒假；
- 大一下；
- 大一暑假；
- ……
- 大四上；
- 大四寒假；
- 大四下。

Stage 本身不复制页面，而是通过规则决定可展示哪些 PlanningType。

## 4. PlanningType

规划类型：

- `GPA`：绩点规划；
- `ENGLISH`：英语规划；
- `COMPETITION`：竞赛规划；
- `RESEARCH`：科研规划；
- `INTERNSHIP`：实习规划。

已确认展示规则：

| 阶段 | 可展示规划 |
| --- | --- |
| 大一至大三正常学期 | GPA / ENGLISH / COMPETITION / RESEARCH |
| 大三暑假前的假期 | ENGLISH / COMPETITION |
| 大四 | INTERNSHIP |
| 大四寒假 | INTERNSHIP |

`INTERNSHIP` 不关联辅导老师和辅导记录展示。

## 5. Plan

某个 Student 在某个 AcademicStage 下的一类具体规划。

示例：

`张同学 -> 大二上 -> 英语规划`

Plan 保存该规划的目标、内容、状态和必要扩展数据。

## 6. CourseTarget

仅用于 GPA 规划的课程级目标。

典型字段概念：

- 课程名称；
- 课程属性/学分（如数据源提供）；
- 课程难度或规划备注；
- 目标分数；
- 实际分数（后续如需要）；
- 备注。

目标分数由辅导业务逻辑确定，不在前端写死。

## 7. Mentor

辅导老师信息。

可供小程序查看老师介绍，并与需要导师信息的规划关联。

实习规划不展示 Mentor。

## 8. CoachingRecord

由后台员工录入的辅导记录。

关联：

- Student；
- Stage/Plan（按最终交互决定粒度）；
- Mentor（如适用）；
- 时间；
- 内容摘要。

实习规划不展示 CoachingRecord。

## 9. School / Program

保研相关院校及项目信息，是 AI 检索和用户浏览的重要数据源。

School 与 Program 分离，避免把一所学校的多个项目压在单一文本字段中。

## 10. Case

真实保研案例。

至少需要区分：

- 来源；
- 是否九辰服务案例；
- 是否允许公开；
- 匿名化状态；
- 学生背景；
- 最终结果。

未经确认不得把外部案例展示为九辰成功案例。

## 11. Assessment

一次 AI 保研评估记录。

概念上保存：

- User；
- 输入快照；
- 使用的数据/知识版本；
- Agent/Prompt 版本；
- 模型标识；
- 结构化结果；
- 调用状态；
- 是否消耗评估额度。

## 12. CreditAccount / CreditLedger

评估额度账户与流水。

不要只在 User 表放一个可任意修改的 `balance` 而没有流水依据。

流水事件可能包括：

- 免费额度发放；
- 微信支付充值；
- AI 评估消费；
- 调用失败退款/回滚；
- 后台人工补偿。

## 13. Payment

只服务于 AI 评估额度充值，不用于课程购买。

需要保存微信侧订单标识、内部订单号、金额、状态、回调处理状态等，并保证回调幂等。

## 14. AdminUser

九辰内部管理后台账号。

P1/P3 至少支持公司员工安全登录并维护学员课堂数据。权限是否进一步拆分为管理员/辅导老师等角色，在进入后台权限实现前冻结。

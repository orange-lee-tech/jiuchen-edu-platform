# 虚拟支付可靠性核对（2026-10-27）

## 协议依据与适用范围

- 微信正式虚拟支付协议是权威来源：`wx.requestVirtualPayment` 道具直购使用 `short_series_goods`，`signData` 原始 JSON 字节参与两种 HMAC；金额单位是分。九辰四个固定 SKU 的金额和 Product ID 配置没有在本次变更中修改。
- 腾讯云维护的接入参考：<https://github.com/TencentCloudBase/skills/blob/main/skills/cloudbase-wechat-integration/references/virtual-payment.md>。发货推送优先，`query_order` 与 `notify_provide_goods` 用于推送缺失时补偿；客户端 success 不是支付证明。
- XPay 公开接口模型：<https://github.com/minibear2021/wechat-xpay/blob/main/docs/apis.md>。`query_order` 的 `status`：0/1 未付款，2/3/4 已付款，5/8 退款，6 关闭，7 退款失败，9/10 平台调整。仅在剩余可退金额 `left_fee=0` 时把 5/8 视为整单退款；部分退款、失败和平台调整进入人工核对。`env_type` 为 1 正式/2 沙箱，区别于请求 `env` 的 0 正式/1 沙箱。`order_type` 仅接受支付单类型，不把退款单作为购买凭据。
- 发货 XML 的道具字段来自 `GoodsInfo`，微信支付字段来自 `WeChatPayInfo`。退款推送以 `RetCode` 区分成功/失败；收到 `refund_order` 的 `errcode=0` 只说明任务启动，不说明退款完成。
- iOS 购买的退款由用户通过 App Store 申请；服务器不主动发起 iOS 退款。

## 本地状态流转

1. 服务端创建 `pending` 订单并固定商品、金额、次数、方案版本；客户端调用微信收银台。客户端失败码只显示诊断。
2. 官方查单或已验签、解密且与本地商品、用户、环境相符的发货推送确认付款；唯一通知、订单和账本事务只发放一次次数。推送确认与主动补发确认使用不同路径。
3. 超过付款窗口的未付款订单，只有本人确认、服务端无任何付款/到账/通知/发货证据且微信查无此单时才能结束；原记录保留。关闭后迟到的付款证据只进入人工财务核对，不能自动再发放。
4. 退款请求是售后核对请求，`open`、`processing`、`succeeded`、`failed` 与 `resolved` 分开。可信退款通知可把整单标为 `refunded`，原学点发放流水保留；部分使用、部分退款或退款失败均需人工核算。售后请求与人工操作有独立记录。
5. 后台补查继续使用现有 worker 和时间间隔，每单最多 64 次；达到上限留下异常记录并停止自动请求。管理员可以人工重查。最近 7 天已关闭订单也在有限次数内观察迟到付款证据。

## 数据库与发布边界

新增 `virtual_payment_cases`、`virtual_payment_case_actions` 两张表及唯一键、索引和外键；不修改或删除既有订单、学点账本、密钥。现有 API 回滚后可忽略新增表。CI 使用临时 MySQL 8 把迁移执行两次，检查既有订单不变、外键、唯一键和审计记录。

生产数据库尚未执行本迁移；必须先只读核对现役结构、完成隔离验证并取得独立生产 DDL 批准。新 API 对这两张表有依赖，不可在缺表的生产库直接切流。

## 尚待官方及真人验证

- 本轮没有调用真实 `refund_order`。该接口的超时重试、部分退款后 `left_fee` 变化和原退款单号复用规则未由当前正式文档明确覆盖；安卓退款先由微信商户后台的人工流程执行，再凭可信推送与官方查单记录结果。iOS 走 App Store。
- 微信账单 `download_bill` 的文件格式、字段映射和可信获取流程尚未通过正式环境样本核实。管理员界面的滚动 24 小时统计只对比九辰订单、学点账本与已核实推送/查单；明确显示微信账单「未接入」，不得称为正式三方日对账。
- 真机需核实四个 Product ID 与金额、收银台、微信支付单、发货推送、到账一次、退款推送与售后状态。单元测试、CI 和 API 健康检查均不能替代真实支付验收。

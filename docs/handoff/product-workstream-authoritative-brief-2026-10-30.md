## 1. 远端代码审计：优先复用什么

以下为当前 GitHub `main` 的源码核验结果。Codex 仍需对本地候选复核，尤其是候选新增文件和迁移。

| 现有结构 | 已有职责 | 本轮使用方式 |
|---|---|---|
| `users`、`teachers`、`user_profiles` | 账户、教师业务档案、学员学术档案 | 老师／管理员资料扩展需明确正式姓名与账号昵称的区别；不要把员工资料塞进学员学术档案 |
| `student_teacher_assignments` | 师生分配关系、主辅导／协助关系 | 教师列表、计划写入和学员数据读取统一以此做服务端授权 |
| `student_plans`、`plan_items` | 阶段规划和任务，含可空截止日期 | 自定义规划继续复用计划和任务模型 |
| `plan_revisions` | 规划版本、提交者和审核状态 | 保留现有教师审核／版本链，不另建平行规划系统 |
| `credit_ledger_entries` | 免费发放、购买发放、评估扣减、管理员调整和纠错 | 指定学员补发次数走账本事件，不直接修改余额 |
| `assessment_ai_calls` | 单次模型调用、Token usage、模型及对象版本观测 | 作为 AI 成本核算的调用级数据基础 |
| `assessment_ai_price_versions`、`assessment_ai_price_heads` | 价格版本与生效头 | 保留人工审核和价格版本追溯 |
| `admin-controls` | 管理员控制盒、PIN、草稿和生效校验 | 新的敏感管理动作复用现有六位 PIN／控制盒机制，不新建第二套 PIN |
| `assessment-key-objects` | AI 服务对象、服务器加密 Key、模型复制和连接测试 | 同一对象内切换模型，扩展现有对象版本和审计机制 |
| `news_posts.tags_json` | 资讯现有标签数据 | 管理员全局标签优先复用；教师私有标签需独立作用域，不能覆盖全局标签 |
| `/me/teacher/students` | 当前教师及已分配学员列表 | 扩展教师工作台读模型；不再保留无必要的“查看我的学员”中转页 |
| `classroom-workspace` | 学期、课表、规划直接保存和近期任务 API | 优先修复现有链路和权限，不另建课堂服务 |

### 1.1 远端主线中已知的缺口

- 教师路由目前主要返回教师资料和已分配学员基本信息；尚未形成课程、规划执行、评估使用、购买／充值的完整教师工作台读模型。
- 远端主线 `PLAN_TYPES` 目前限定 GPA、英语、竞赛、科研、实习五类；`student_plans.type` 与 `plan_revisions.type` 也有固定枚举。自定义规划需要扩展既有模型和迁移，不能只加前端选项。
- 远端主线的 `profile.ts` 是学员学术档案接口；教师和管理员没有完整的员工资料模型。
- 远端主线教师 API 未见个人待办完整闭环。
- 远端主线资讯数据有 `tags_json`，但没有已核验的教师专属标签作用域和面向学生的组合读取逻辑。
- `copyAssessmentKeyForModel` 是复制服务对象的路径；本轮需要同一服务对象内切换模型。
- `assessment-ai-cost.ts` 会记录模型调用 Token usage；DeepSeek 价格来源检查当前只抓取官方页面并存储来源摘要，价格仍需人工审核保存。
- `commercial-analytics.ts` 的供应商风险参考依赖环境变量余额快照和单次成本估算；远端主线不能据此认定已经实现实时供应商账户余额读取。
- 远端主线未见 `teacher_todos`、`ai_balance_snapshots` 的迁移文件；若本地候选已有，必须核验其实现和迁移，不得重复建表。

## 2. 本轮产品需求与验收口径

### A. 老师／管理员个人资料

**目标：** 老师和管理员在「我的」页面都能进入自己的资料卡，补全正式身份资料。

字段：

- 真实姓名；
- 手机号码；
- 工作部门；
- 直属领导。

要求：

1. 老师和管理员都能查看、编辑自己的资料。
2. 管理员能在管理端查阅教师正式姓名及资料完整度。
3. 员工正式姓名与微信账号昵称／`users.displayName` 必须区分。
4. 教师业务档案中的 `teachers.name` 当前承担正式业务名称；Codex 应先核对其使用范围，再确定员工资料的单一权威来源和同步策略。
5. 不得把员工资料写入学员学术档案字段，不得把昵称静默当作实名。
6. 手机号属于个人信息：仅本人及明确授权的管理员可查看；不得暴露给其他学员或无关教师。
7. 如使用微信手机号快速验证，遵循微信官方能力和现有隐私授权流程；不得在本轮擅自建立短信账号体系。
8. 新增字段需有服务端校验、权限测试和必要迁移；保留旧账号与旧身份绑定。

**验收：** 老师和管理员分别填写、重新进入后仍能读取；管理员可看到教师实名完整度；普通学员和非分配教师不能读取员工手机号等隐私资料。

### B. 教师工作台：直接完成学员规划

**目标：** 教师进入「工作台」即可规划，不再先进入“查看我的学员”再开始操作。

工作台规划区应具备：

1. 学员选择器：只列出当前教师有效分配的学员。
2. 可切换当前学员；切换后显示该学员真实阶段、已有规划和任务。
3. 支持单学员规划。
4. 支持多选学员，将同一套模板／规划方案分别应用到多个学员。
5. 支持保存、命名、编辑、复制和删除教师自己的规划模板。
6. 规划模板应用后，为每位学员生成独立的 `student_plans`、`plan_items` 数据；后续编辑模板不得反向修改已生成的学员规划。
7. 批量应用必须逐个核验教师与学员的有效分配关系；事务／失败处理清楚，向教师返回成功与失败名单；不得因为某一个学员失败而静默丢失其他结果。
8. 保留原有学生规划、教师直接保存、审核和 `plan_revisions` 版本机制。
9. 不把批量规划实现成绕过教师权限的管理员接口。

### C. 教师自定义规划路径

现有标准模板继续保留：

- GPA；
- 英语；
- 竞赛；
- 科研；
- 实习。

新增**自定义规划**入口，允许教师针对特殊安排创建自由命名的规划，例如大四上除实习之外的个人安排。

要求：

1. 自定义规划仍然属于现有学期／阶段规划体系。
2. 至少支持自定义规划名称、任务名称、目标、截止日期和状态。
3. 能保存为教师模板，并应用给单个或多个已分配学员。
4. 不强制绑定大四实习模板，也不破坏既有标准模板。
5. 通过 migration 扩展类型／模板存储；保留历史五类计划和旧记录。
6. 学员端、教师端、管理员只读查看端使用同一套计划数据和状态语义。
7. 旧规划不得因为类型枚举扩展而被重写或丢失。

### D. 教师工作台：学生服务信息总览

教师职责不仅是“给学生写规划”，还包括了解自己所负责学生的学习和服务情况。

教师工作台／学员列表至少展示：

- 学员身份与当前阶段；
- 课表是否已建立、当前课程情况；
- 阶段规划数量、近期任务和执行状态；
- AI 评估使用情况（次数、最近使用时间、成功／失败状态等）；
- 充值／购买情况（订单状态、购买次数、到账情况等）。

要求：

1. 复用现有课表、规划、评估、订单和额度账本数据。
2. 优先扩展现有教师学员列表读模型或建立一个聚合只读接口，不为每个字段随意新增独立接口。
3. 所有数据必须由服务端根据当前教师身份和有效 `student_teacher_assignments` 过滤。
4. 教师只能看到自己有效分配的学员；协助教师按有效关系读取其获准范围。
5. 教师可看学员充值／购买记录的必要业务摘要，但不能修改订单、补发次数、退款或查看供应商账单。
6. 教师不得查看学生以外的 AI API Key、供应商账户余额、公司成本或其他教师的学生数据。
7. 管理员既有全局只读权限不被削弱，也不得把教师权限扩展成管理员权限。

### E. 教师个人待办

截图中「个人待办」已有 UI，但点击后出现“当前服务暂不支持此操作”。

要求：

1. 修复真实服务端读写链路，不允许只把提示语改掉。
2. 教师可新增、编辑、完成、删除自己的待办。
3. 支持标题／内容和可选截止日期；未设置截止日期合法。
4. 待办严格按当前教师账号隔离。
5. 重新进入页面可回读；失败原因明确并有重试。
6. 如果本地候选已有 `teacher_todos` 表和迁移，先核验并复用，不得再建第二张表。
7. 如需要新增迁移，支持重复执行和旧数据保护。

### F. 教师「辅导」页信息架构与资讯标签

**页面结构：** 删除教师「辅导」页中的“跟进学员的成长”入口卡片；该一级菜单只保留：

- 院校库；
- 资讯。

这里只移除该页的成长跟进入口，不删除成长档案数据、API 或其他角色仍在使用的成长能力。

**资讯标签：**

1. 管理员设置的标签是全局标签，对所有符合展示权限的学员生效。
2. 教师设置的标签只对该教师当前有效分配的学员生效。
3. 管理员标签与教师标签并存，不能相互覆盖或删除。
4. 一个学员有多个有效教师关系时，按产品确认的有效关系汇总可见教师标签；不得读到无关教师的标签。
5. 教师只能管理自己设置的标签和自己获准管理的资讯；管理员可管理全局标签。
6. 学员端显示全局标签与其有效教师的标签，并能区分来源或作用域。
7. 资讯标签只用于分类／筛选和内容运营，不得伪装成资讯来源的原始标签。
8. 优先复用 `news_posts.tags_json` 的全局标签能力；教师标签采用独立的 teacher scope 关系，不能把多个教师标签写入全局 JSON 后导致泄漏。

### G. 教师「学员」一级菜单

当前页面只有“查看我的学员”按钮，属于多余的中转层。

要求：

- 进入「学员」一级菜单后直接展示已分配学员列表；
- 有搜索／筛选时复用现有能力，没有则不为了装饰增加复杂筛选；
- 空列表显示清楚的空状态；
- 点击具体学员仍可进入详情；
- 工作台规划区不依赖先进入此页。

### H. 管理员工作台入口

在现有管理员工作台增加两个入口：

1. **资讯标签管理**：进入管理员全局资讯标签管理。
2. **API 密钥管理**：优先作为现有 AI 服务管理／密钥对象管理的入口或快捷入口。

约束：

- API 密钥管理只管理当前已实现的 AI Provider 服务对象及其加密 Key。
- 不在小程序端显示 Key 明文。
- 不新建一套通用 Secret Vault，不复制现有服务对象存储。
- 微信 AppSecret、支付私钥、腾讯云 CAM Key 等系统级 Secret 不因此暴露给小程序管理界面。
- 现有 AI 服务管理页面继续是密钥写入、连接测试和版本切换的唯一权威操作路径。

### I. 管理员向指定学员发放指定评估次数

新增管理员操作区：

- 选择指定学员／账号；
- 输入发放次数；
- 必填发放原因；
- 显示发放前后余额；
- 使用现有生效的六位 PIN 机制验证；
- 提交后显示结果和审计信息。

实现要求：

1. 复用 `credit_ledger_entries` 的 `admin_adjustment` 类型或现有受控调整服务。
2. 必须服务端鉴权，不能只在前端校验 PIN。
3. 使用事务、幂等键和审计记录，防止重复点击重复发放。
4. 记录操作者、目标用户、增减数量、原因、时间、账本事件 ID。
5. 禁止直接 UPDATE 用户余额或篡改支付订单。
6. 不能修改历史订单的金额、SKU 和购买次数快照。
7. 不能通过这项能力改变全局免费赠送方案或固定售价。

### J. AI 服务对象与模型目录

**当前问题：** 模型选择列表选项太少、命名不清楚；同一供应商下有重复服务对象，弹窗难以区分；切换同一服务商模型需要复制／新建对象，操作繁琐。

要求：

1. 模型选择器尽量采用各供应商官方模型 ID 和官方名称。
2. 按供应商展示经核实的可用模型目录；标明模型 ID、能力／用途、官方来源和最近核验日期。
3. 保留自定义模型 ID 输入，官方目录未覆盖时仍可使用兼容模型。
4. 不凭空编造模型名、速度标签或模型能力。
5. 服务对象选择器至少区分：服务对象标签、供应商、模型 ID、对象版本、当前启用状态、最近更新时间。
6. 同一服务对象内可切换模型，不要求复制或新建服务对象。
7. 切换模型只更新该对象的模型配置和版本；保留原 Provider、API Base URL、加密 Key、对象 ID 和创建关系。
8. 切换生效前复用现有六位 PIN／控制盒机制；写入审计事件。
9. 切换后重新执行连接测试／报告格式验证；失败时不得替换当前生效对象。
10. 原有“复制模型”能力可保留作独立操作，但不再是同一服务对象切换模型的唯一方式。

### K. AI 官方余额、预警与单次评估成本

这是本轮最需要先核实、再决定 UI 的问题。

#### K1. DeepSeek 官方余额接口

DeepSeek 官方文档提供只读余额接口：

- `GET https://api.deepseek.com/user/balance`
- 官方说明：[Get User Balance](https://api-docs.deepseek.com/api/get-user-balance/)
- 返回字段包括 `is_available`、`balance_infos`、币种、`total_balance`、`granted_balance`、`topped_up_balance`。

截图中出现的 `CNY 9.12` 和读取时间，可能来自该类接口，但必须追踪本地候选的实际 API 请求、使用的服务对象／Key、响应解析和前端绑定，确认不是人工输入、测试值或旧快照。

#### K2. 余额读数与评估费用的边界

**余额是供应商账户级快照，不是单次请求账单。** 余额差值只有在调用期间没有其他并发请求、其他系统共用该账户、充值／赠送余额变化、结算延迟或其他消费时，才可能被可靠归因给单次评估。

因此要求：

1. 首先验证真实供应商接口、认证 Key、币种、时间戳、读数新鲜度和错误状态。
2. 如果支持，自动读取余额，设定管理员可调整的最低余额阈值，低于阈值预警。
3. 记录每次评估完整执行窗口的前后余额快照；一次评估可能包含初次调用和修复调用，不能只看第一条模型请求。
4. 检查同一服务对象并发调用、同一账户被其他业务共享、余额结算延迟和人工充值等情况。
5. 只有能证明独占窗口和可归因时，才把余额差值标为“已对账的评估实际差额”；否则标记为“账户差额，未分配”，不得强行贴给某一学员或评估。
6. 继续使用 `assessment_ai_calls` 中供应商返回的 Token usage 和经过审核的价格版本，形成调用级成本估算／核对数据。
7. 供应商余额变化用于账户总额核对；Token usage × 已审核官方价格用于单次调用成本估算。两者分层展示，不混成一个看似精确的数字。
8. 成本记录区分 `estimated`、`reconciled`、`unallocated`、`unavailable` 等状态，并保留来源和时间。
9. 余额接口不可用或读数过期时，显示清楚的降级状态和最后成功读取时间；不能显示旧数值为实时余额。
10. 如果自动余额读取经真实链路验证可靠，移除日常操作中重复的人工余额录入负担；可保留管理员手动核验作为明确标记的 fallback，不把人工数值冒充自动读数。
11. 保留学生评估次数账本与供应商 API 余额账本的分离：前者是用户业务次数，后者是公司供应商账户余额。

#### K3. 官方价格抓取

1. 现有 DeepSeek 价格来源检查先抓取页面并记录来源摘要；这不等于自动解析价格。
2. 只有余额接口不能覆盖的成本核算场景才继续完善价格抓取。
3. 从官方价格页解析为“待审核草稿”，展示模型、输入／缓存命中／缓存未命中／输出价格、币种、单位、峰谷时间规则、来源 URL、抓取时间和解析版本。
4. 管理员审核后才生成价格版本；不得自动覆盖当前生效价格。
5. 页面解析失败时保留当前已审核价格并显示原因，提供人工补录 fallback。
6. 对价格解析器使用官方页面快照／fixture 测试，防止页面改版导致静默错价。
7. 管理员界面使用通俗说明；专业字段可折叠展示，避免要求运营人员理解不必要的底层细节。

### L. “当前服务暂不支持此操作”异常收口

截图中至少涉及个人待办和人工核验 API 余额操作。

要求：

1. 追踪真实请求 URL、HTTP 状态、服务端错误码、响应结构和权限。

### N. 学员「今天」页近期任务

## 6. 推荐 Codex 模型

本轮属于跨前端、API、数据库、权限、账本、供应商接口和 ECS 发布准备的综合工程，建议优先投入最高质量的推理额度：

- 如果 Codex 当前模型选择器明确提供更适合代码施工的专用模型，且其推理档位高于 GPT-6 可用档，可选择该界面实际提供的最高能力档；不要根据旧模型代号或未经核实的名称猜测。
- 对跨模块架构审查、数据库迁移设计、权限与账本审计、最终集成验收，始终由主施工模型负责。

- 预算允许优先保证主模型推理质量，不要为了节省额度把核心架构判断交给低能力模型；也不要把多个 Agent 同时修改同一批共享文件当成“更快”。

**施工总要求：先读本文件和本地候选，再报告差异；确认工作区安全后施工。目标是把现有业务闭环补齐，而不是另起一套系统。**
